pySCAtter: validation against CrystalScatter

pySCAtter was compared pixel by pixel with the CrystalScatter C++ code (SasScatter2, console build sas_scatter2Cons). Both programs got the same parameter file, and pySCAtter evaluated its model at the q vectors of the C++ image.

Method

  • C++ build. The C++ code was built with qmake6 (Qt 6). Two small patches were needed:

    • #include <chrono> and QLatin1String in XMLCOMP, to compile;

    • the console’s generateSingleImage writes q_x, q_y, q_z and I of every pixel to a text file and skips the parameter check, which otherwise aborts some runs.

  • Images. 128 × 128 pixels in preset mode (q_max = 2 nm⁻¹, GridPoints = 64). The C++ (q_x, q_y, q_z) maps to the engine’s (q_y, q_z, q_x).

  • Orientation. The lattice cases of the table are isotropic. pySCAtter then uses the powder form of the lattice factor, without the azimuthal factor. Until 13 November 2026 the azimuthal factor was applied for the isotropic orientation too whenever EditAzi > 0, which gave single-crystal spots. The lattice rows below were obtained before that correction and have not been re-run since.

  • Statistics. For every case:

    • the median ratio C++/pySCAtter, which is the scale;

    • the median, 95th percentile and maximum of |ratio/scale − 1|;

    • the maximum restricted to pixels with I > 10⁻⁴ I_max.

The tests in tests/scatter/test_cpp_lattice.py check the width modes:

  • the Gaussian FWHM is √(π ln 2)·4/D, independent of the lattice constant;

  • the Lorentzian FWHM is 4/D;

  • the paracrystal width grows as 4/D + c g²;

  • the Debye–Waller factor is exp(−σ²q²/3).

Changes made in pySCAtter to match the C++ code

  • Peak width. δ = 4/D (Debye–Scherrer), the paracrystal width 4/D + (σ/d_nn)² d_nn q², or the fixed width 1. The two radio buttons became the peak width combo of the Model panel.

  • Lattice factor. The lattice factor now has the C++ form: g₃ = 2π/g² at the reflection, the azimuthal normalisation N(g), and the peak shapes with the C++ constants.

  • Pseudo-Voigt. η = PeakPar/100, as in the C++ code; it was PeakPar before.

  • Reflections. Only reflections with |h|, |k|, |l| ≤ HKLmax are used. pySCAtter used HKLmax + 3 before, which changed the diffuse level between the peaks by up to 15 %.

  • Debye–Waller factor. G(q) = exp(−σ_DW² q²/3) from EditDebyeWaller. EditBFactor is ignored, as in the C++ code.

  • Lengths. The cylinder Length is the half-length; the disk takes EditRadius as the half-thickness and Length as the radius; the vesicle takes EditRadius as the inner and Length as the outer radius. σ and σ_L are independent distributions.

  • Director. The director (θ, φ) is defined in the C++ frame: θ = 90°, φ = 90° is vertical on the detector.

  • Narrow distributions. A Schulz average on a uniform grid replaces the Gauss–Laguerre rule for narrow distributions (z > 140). The Laguerre rule gave NaN there.

  • Isotropic lattices. The azimuthal factor is left out for the isotropic orientation (powder rings), and I(q) is always the powder average.

  • Cell parameters. Cubic lattices use a only, bct and hcp a and c, the cylinder packings a (hexagonal) or a, b, γ, and lamellae a.

Defects and approximations found in the C++ code

These are left as they are in the C++ code. pySCAtter follows the C++ code where it is a convention, and the physics where it is an approximation or a defect.

  1. Sphere pq3 term. A typo in the asymptotic sphere expression causes up to 6 % error for narrow distributions (σ = 0.02), near the minima.

  2. Core/shell ac9 term. A wrong coefficient in the core/shell cross term. pySCAtter uses the correct form.

  3. Cylinder factorisation. For L/R ≥ 2 the C++ code computes P ≈ P_rod·P_cs instead of the orientation average of the product. The isotropic curve differs by 1–2 % (up to 17 % near minima). For oriented cylinders the cross-section factor is evaluated at |q| instead of q_⊥, which strongly suppresses the streak perpendicular to the axis. pySCAtter keeps the exact average.

  4. Disk. The C++ disk formula gives wrong values for Length < EditRadius. For proper disks it differs from the exact average by 1–4 % at mid q and by about 15 % at high q.

  5. Modified Lorentzians. The denominators use c₁ = 4 while the prefactors use c₂ or c₃. The peak areas are 0.64 and 0.77 instead of 1. pySCAtter reproduces this.

  6. Pseudo-Voigt. The Gaussian normalisation peaknorm2 is never set, so the intensity scales as 1/η. pySCAtter reproduces this.

  7. Gamma peak. It is not implemented (#ifdef undef), which gives s_q = 1.

  8. No check of D. Domain sizes smaller than the unit cell are accepted without a warning.

  9. Cube. The C++ code switches to the Porod asymptote at high q, which gives tails up to 40 % different.

  10. Spheres on a lattice. A residual of up to 5 % appears between the peaks, in a band of q starting where qR ≈ 5. It is probably in the C++ amplitude ⟨F⟩ but has not been traced.

Not yet compared

  • Core + shell ellipsoid. The C++ run ends without output.

  • Excluded-volume chain. The C++ output is empty.

  • Inhomogeneous shell. The C++ definition differs (probably a power-law profile); the median difference is 60 %.

  • Core + shell cylinder. It differs by 44 %, because of the length convention in the shell branch.

  • Superball. The C++ run takes more than 10 min per image.

  • Oriented lattices. The zone-axis and ψ rotation conventions are not compared yet. Rod and lamellar lattices are rotated by the zone axis and ψ since November 2026; how the C++ code orients them has not been checked.

  • Hexagonal cylinders and lamellae on a lattice. The diffuse part differs by a smooth factor of 0.2–0.6. The C++ code probably uses a different particle term in the 2D-lattice branch; this is not resolved. The comparison was made before the rotation of these lattices was introduced and has to be repeated with it.

  • Wiring. Whether every parameter and combo entry reaches the calculation is checked by tests/scatter/test_wiring.py within pySCAtter (see the main page); it is not a comparison with the C++ code.

  • Kratky–Porod chain, Teubner–Strey and the structure factors. These exist only in pySCAtter. They are checked against their analytic limits (see the main page).
